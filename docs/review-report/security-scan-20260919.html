攻擊情境

持有群組密碼者送出 HostInputsChanged，host_id 為約 7KB 的字串、input 為某主機目前佔用的 port，藉「頂掉衝突」讓短路生效，垃圾條目寫入 settings.json。受害主機的 Ping 回應整包附上 host_inputs，超過 8KB 後被 client 截斷、JSON 解析失敗；而每次切換到該主機前都必須 Ping 成功，因此該主機永久無法被切換或同步，只有「重設全部」能復原。即使沒有攻擊者，多主機 × 多螢幕的 tombstone 與已移除主機條目也永遠不會清理，長期會自然逼近上限。與既有 alias／label 的 MAX_SHARED_*、is_valid_host_id 慣例不一致。

附帶功能 bug：同一個短路也讓合法更新在「頂掉衝突」時，不會把新 port 套用到目標主機（set_input_for／local_input 不執行），只寫入帳本，造成帳本與實際設定不一致。

修復
在迴圈開頭驗證 host_id 必須是 local_host_id 或 peers 之一，並通過 host_order::is_valid_host_id；先解析目標主機再處理衝突（移除 || 短路）；新增 MAX_SHARED_HOST_INPUTS，超量整包拒收；remove_peer、取消共用螢幕、重設時修剪無關條目，tombstone 設 TTL；Ping 回應與快照序列化後檢查大小預算。

src-tauri/src/lib.rs:4248 · 4343（record_host_input_update）· 1310-1312（重設）· 3425
證據
if update.updated_at_ms <= current_version { return None; }   // 未對未來值夾限
// 本機後續編輯：now_ms.max(previous.saturating_add(1)) → 永遠停在 u64::MAX
攻擊情境

持密者送一筆 updated_at_ms = u64::MAX 的 tombstone，即可讓某主機在某螢幕的 port 指派被永久清空，之後任何人（包括本機 UI 與「重設螢幕」）都改不回來。非惡意情境：某台主機時鐘曾大幅超前（CMOS 電池沒電），那段期間的編輯進入 outbox，NTP 校正後送出的未來時間戳會一直「贏」到真實時間追上為止。

修復
接收端拒收或夾值 updated_at_ms > now_ms + MAX_CLOCK_SKEW(30s) + 容忍值（協定已要求 ±30 秒時鐘差，不會誤傷正常主機）；record_host_input_update 拒絕未來值的 previous。既有的 alias／label／host_order 合併有同樣缺口，建議一併修。

LAN 協定核心（Rust · OWASP API Top 10 2023）

認證架構（重點檢查）：
  • 配對密碼（≥15 字元）經 PBKDF2-HMAC-SHA256 600,000 次拉伸；請求以 HMAC 簽 (timestamp, nonce, action) 全訊息，verify_slice 常數時間比較；±30 秒時鐘偏移＋nonce 表防重放（有回歸測試）。
  • 回應同樣簽章並綁定請求 nonce；mDNS 探索到的位址變更需先以密碼證明（confirmed_move）才採信。
  • 核心限制：群組共享對稱密鑰只能證明「發送者是群組成員」，無法證明訊息內聲稱的 host_id（見 A-F2，以及未 commit 改動的 D-M1／D-M2 使其影響放大）。
